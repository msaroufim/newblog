Layer 1

Host & launch scheduling

Deciding when work enters the GPU, and shaving the CPU→GPU round trips off the critical path.

≈ µs regimeTop of the stack: decisions about whole kernels. Everything here fights the microsecond world of the latency ladder — launch machinery, host round trips, kernel-boundary gaps. Every layer below refines the assignments made here, inside the box this layer freezes at launch time (grid, block, cluster dims, smem carve-out). Its central seam is the kernel boundary: when a boundary costs too much, layer 1 softens it (graphs pack it, PDL overlaps across it) — the alternative, dissolving it entirely, lives one layer down.

Streams & events

all archsruntime APIthe substrate

A stream is an in-order command queue; work in different streams may overlap. Events express dependencies between points in stream command sequences: a waiter cannot pass until everything preceding the event record has completed. Use nonblocking streams deliberately: the legacy NULL stream can introduce implicit synchronization, while per-thread default-stream mode changes that behavior. Transfer overlap and directionality are device-specific; query asyncEngineCount and verify the actual timeline in Nsight Systems.

s1, s2 = Stream(non_blocking=True), Stream(non_blocking=True)

launch(kernel_a, stream=s1)                   # these two can
copy_async(dst, src, to="device", stream=s2)  # run concurrently

ev = Event(timing=False)                      # cheaper than timed
ev.record(stream=s1)
s2.wait(ev)                                   # cross-stream dependency
launch(kernel_b, stream=s2)                   # runs after ALL of kernel_a
cudaStream_t s1, s2;
cudaStreamCreateWithFlags(&s1, cudaStreamNonBlocking);
cudaStreamCreateWithFlags(&s2, cudaStreamNonBlocking);

kernelA<<<grid, block, 0, s1>>>(...);                      // these two can
cudaMemcpyAsync(dst, src, n, cudaMemcpyHostToDevice, s2);  // run concurrently

cudaEvent_t ev;
cudaEventCreateWithFlags(&ev, cudaEventDisableTiming);     // cheaper than timed
cudaEventRecord(ev, s1);
cudaStreamWaitEvent(s2, ev, 0);                            // cross-stream dep
kernelB<<<grid, block, 0, s2>>>(...);                      // waits on ALL of kernelA

Use when

  • Independent kernels or copies serialize in the default stream
  • Overlapping transfers with compute (use pinned host memory)
  • As the substrate every other technique builds on

Limits

  • Dependencies are whole-kernel: B's first block waits for A's last
  • Each launch costs ~2–10 µs of CPU time
  • Concurrency is opportunistic — a big kernel fills all SMs anyway

Stream priorities

all archsruntime API

A hint to the hardware scheduler about which stream's pending blocks to dispatch first as SMs free up. Lower numbers are higher priority. The classic use: keep NCCL/communication kernels from starving behind a wave of GEMM blocks.

lo, hi = device.stream_priority_range()      # hi is numerically smaller
comm    = Stream(non_blocking=True, priority=hi)
compute = Stream(non_blocking=True, priority=lo)
# per-launch override also exists via launch attributes
int lo, hi;
cudaDeviceGetStreamPriorityRange(&lo, &hi);   // hi is numerically smaller
cudaStream_t comm, compute;
cudaStreamCreateWithPriority(&comm,    cudaStreamNonBlocking, hi);
cudaStreamCreateWithPriority(&compute, cudaStreamNonBlocking, lo);
// per-launch override also exists: cudaLaunchAttributePriority

Use when

  • Latency-critical kernels (comm, decode attention) contend with bulk compute
  • Cheap to try — one line at stream creation

Limits

  • No preemption of already-running blocks — only dispatch order
  • For hard guarantees, reserve SMs with green contexts instead

Stream-ordered memory allocation

all archsCUDA 11.2+

Not scheduling of compute, but scheduling of allocation: cudaMallocAsync/cudaFreeAsync enqueue alloc/free into a stream instead of synchronizing the device the way cudaMalloc can. Removes a classic source of hidden serialization between otherwise-overlapping streams, and memory pools let freed blocks be reused without OS round trips.

p = malloc_async(nbytes, stream=s)            # ordered within stream s
launch(kernel, args=[p], stream=s)
free_async(p, stream=s)                       # safe: ordered after the kernel

pool = device.default_mempool()
pool.release_threshold = UNLIMITED            # keep freed memory cached
void* p;
cudaMallocAsync(&p, bytes, s);      // ordered within stream s
kernel<<<g, b, 0, s>>>(p);
cudaFreeAsync(p, s);                // safe: ordered after the kernel

cudaMemPool_t pool;                 // keep freed memory cached in the pool
cudaDeviceGetDefaultMemPool(&pool, dev);
uint64_t huge = UINT64_MAX;
cudaMemPoolSetAttribute(pool, cudaMemPoolAttrReleaseThreshold, &huge);

Use when

  • Allocation sits inside a hot loop or between pipelined kernels
  • Building graphs (graph memory nodes use the same machinery)

Limits

  • Pointers are stream-ordered — using them in another stream needs an event dep

CUDA graphs

all archsruntime APIlaunch-bound workloads

Capture a whole DAG of kernels, copies, allocations and host callbacks once; instantiate; replay with a single CPU call. The driver pre-resolves dependencies and packs dispatch, collapsing per-kernel launch overhead (~µs each) into ~one. vLLM and TensorRT-LLM use graphs by default for LLM decode.

with s.capture() as g:                        # record a whole decode step
    launch(qkv,  stream=s)
    launch(attn, stream=s)
    launch(mlp,  stream=s)
exec_graph = g.instantiate()

for step in range(N):
    exec_graph.launch(stream=s)               # one CPU call replays everything

exec_graph.update_node_params(node, new_params)  # new ptrs, no re-instantiate
cudaGraph_t g; cudaGraphExec_t ge;
cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal);
qkv<<<ga, b, 0, s>>>(...);
attn<<<gb, b, 0, s>>>(...);        // an entire decode step
mlp<<<gc, b, 0, s>>>(...);
cudaStreamEndCapture(s, &g);
cudaGraphInstantiate(&ge, g, 0);

for (int step = 0; step < N; ++step)
    cudaGraphLaunch(ge, s);          // one CPU call replays everything

// update params without re-instantiating (new seq len, new ptrs):
cudaGraphExecKernelNodeSetParams(ge, node, &newParams);

Use when

  • Many small kernels with a repeating, mostly-static structure
  • CPU launch time shows up as gaps between kernels in the profiler
  • You want PDL/priority attributes baked into a replayable unit

Limits

  • Topology changes force re-instantiation (params can be updated in place)
  • Capture forbids illegal ops (sync, default-stream use) inside the region

Device graph launch

CUDA 12.0+check target support in the feature survey

A kernel launches a pre-instantiated graph from the GPU — device-side scheduling of structured work, without a CPU round trip. Think of it as dynamic parallelism for whole pipelines: a dispatcher kernel inspects data and fires the appropriate graph.

exec_graph = g.instantiate(device_launchable=True)   # host, ahead of time
exec_graph.upload(stream=s)

@kernel
def dispatcher(work: GraphExec):
    if thread.is_leader and work_available():
        work.launch(stream=FIRE_AND_FORGET)   # GPU decides, no CPU round trip
// host: instantiate for device launch, upload
cudaGraphInstantiate(&ge, g, cudaGraphInstantiateFlagDeviceLaunch);
cudaGraphUpload(ge, s);

__global__ void dispatcher(cudaGraphExec_t work) {
    if (threadIdx.x == 0 && work_available())
        cudaGraphLaunch(work, cudaStreamGraphFireAndForget);
}

Use when

  • The decision of which pipeline to run lives in GPU data
  • Self-scheduling pipelines: a graph's last node relaunches it (tail launch)

Limits

  • Graphs must be instantiated/uploaded ahead of time; restricted node types

Conditional graph nodes

CUDA 12.3+ (IF/WHILE), 12.8+ (ELSE/SWITCH)

IF / IF-ELSE / WHILE / SWITCH nodes evaluated on-device: a kernel sets a condition handle, and the graph itself decides whether (or how many times) to run an embedded subgraph. This moves loop and branch control flow off the CPU entirely — e.g. "keep iterating the solver until converged" as one graph launch.

handle = graph.conditional_handle(default=1)

@kernel
def check(residual, handle):
    set_conditional(handle, residual[0] > TOL)   # 1 = run body again

body = graph.add_while_node(handle)              # build the loop body in `body`
cudaGraphConditionalHandle h;
cudaGraphConditionalHandleCreate(&h, graph, 1,
                                 cudaGraphCondAssignDefault);

// inside a kernel that runs before the conditional node:
__global__ void check(float* residual, cudaGraphConditionalHandle h) {
    cudaGraphSetConditional(h, *residual > TOL);  // 1 = run body again
}
// add node: params.conditional.type = cudaGraphCondTypeWhile;
// then build the loop body inside params.conditional.phGraph_out[0]

Use when

  • Iterate-until-converged loops currently synchronized on the CPU
  • Data-dependent branches between captured pipelines

Programmatic dependent launch (PDL)

CC 9.0+ for overlapCUDA 12-era API (11.8 preview)composes with graphsPTX griddepcontrol.wait / .launch_dependents

Normally kernel N+1 in a stream waits for all of kernel N. PDL splits what stream ordering normally fuses into two separate dependencies: launch readiness (when may B's blocks start? — the trigger, a scheduling signal that guarantees nothing about memory visibility) and data readiness (when may B consume A's output? — the grid sync, after which A's writes are visible). The secondary launches early, runs its prologue (weight loads, TMA descriptor setup) concurrently with the primary's tail, and blocks only at the data dependency it declares by hand. Standard trick in TensorRT-LLM and fast GEMM chains for erasing the inter-kernel bubble.

Use when

  • Chains of short dependent kernels where launch + prologue ≈ runtime
  • Inference pipelines; also as PDL edges inside captured graphs

Limits

  • Correctness is on you: touch dependent data before the sync → race
  • Overlap is opportunistic — needs free SMs during the primary's tail
Granularity fine print — the dependency stays grid-shaped: all of A, to each CTA of B. The trigger is collective — B's early launch is gated on every CTA of A executing cudaTriggerProgrammaticLaunchCompletion (or exiting), so put it on a path all CTAs take, and note that A's slowest CTA sets the trigger time. B's blocks each wait independently at cudaGridDependencySynchronize with no tile-to-tile pairing — PDL cannot express "B's tile 7 waits only on A's tile 7"; that fine-grained shape belongs to megakernel counters and MPK events. Overlap materializes at CTA granularity along A's drain curve (a tail-wave-heavy predecessor is the ideal PDL setup), and if B launches as clusters, whole clusters' worth of co-located SMs must free before B can place — larger clusters make the early launch lumpier. PDL×cluster support details have shifted across CUDA versions; check your toolkit.
When it pays — the bound and the ladder — the win is capped at roughly min(primary's trailing phase, secondary's independent prefix), and only materializes given free SMs and complementary resources (a memory-bound prefetch prologue under a compute-bound tail overlaps; two bandwidth-hogs fight). That's why early start isn't a default: the attribute is a promise — "everything before my explicit wait is independent of the predecessor" — that trades away the stream's strongest guarantee, and blanket-enabling it risks races for kernels not written to the contract while buying nothing for kernels with no useful prefix. (If the primary never triggers explicitly, the implicit end-of-kernel trigger still erases the launch-gap — you lose only the deeper tail overlap.) The decision ladder: fuse if it cleanly kills the global-memory round trip → separate streams if truly independent → plain ordering if fully dependent with no prefix → PDL when dependent overall but the successor owns a valuable independent prefix — the canonical case being chained GEMMs, where layer N+1's weights depend on nothing layer N produced, so their prefetch hides under N's tail at every layer of every step.

Launch completion events

target-dependentextended launch API

An event that fires at the documented launch-completion point—after all CTAs have been launched, not after the kernel has finished. Another stream can wait for launch ordering without waiting for output readiness. This does not mean all CTAs are simultaneously resident and is not a data-completion dependency.

ev = Event()
launch(big_kernel, stream=s1, completion_event=ev)  # fires when all CTAs LAUNCHED
s2.wait(ev)          # s2 dispatches only after big_kernel occupies the GPU
                     # (launch ordering — not completion, not data readiness)
cudaEvent_t ev; cudaEventCreateWithFlags(&ev, cudaEventDisableTiming);
cudaLaunchAttribute a{};
a.id = cudaLaunchAttributeLaunchCompletionEvent;
a.val.launchCompletionEvent.event = ev;
a.val.launchCompletionEvent.flags = 0;
cudaLaunchConfig_t cfg{grid, block, 0, s1, &a, 1};
cudaLaunchKernelEx(&cfg, big_kernel, ...);
cudaStreamWaitEvent(s2, ev, 0);   // launch ordering only; outputs may be unfinished

Stream memory operations & external semaphores

driver APIinterop / device queues

Streams can wait on or write device-visible memory words without an event or polling kernel. External semaphores order CUDA against Vulkan, Direct3D, NvSciSync, NIC, or other external timelines. Graphs also have event-record/wait and external-semaphore nodes.

s.wait_value(doorbell, READY, cmp="eq")   # stream stalls until *doorbell == READY
launch(kernel, stream=s)
s.write_value(done, 1)                    # stream publishes progress

sem = import_external_semaphore(handle)   # interop: Vulkan / NIC / other process
s.wait(sem);  launch(kernel, stream=s);  s.signal(sem)
// driver API: queue work only after *doorbell reaches READY
cuStreamWaitValue32(s, d_doorbell, READY, CU_STREAM_WAIT_VALUE_EQ);
cuLaunchKernel(..., s, ...);
cuStreamWriteValue32(s, d_done, 1, CU_STREAM_WRITE_VALUE_DEFAULT);

// runtime interop after importing cudaExternalSemaphore_t sem:
cudaWaitExternalSemaphoresAsync(&sem, &waitParams, 1, s);
kernel<<<g,b,0,s>>>(...);
cudaSignalExternalSemaphoresAsync(&sem, &signalParams, 1, s);

Use when

  • Device queues, doorbells, graphics/compute interop, or external producers
  • A memory value is the natural dependency rather than a CUDA event

Limits

  • Capability, memory visibility, and flags are platform-specific
  • Use batch memory operations when many waits/writes must be submitted together
Layer 2

Device-side grid scheduling

Kernels that schedule themselves: deciding which block does which work, after launch.

µs → 100s of nsOne refinement down: from "which kernel" to "which block gets which tile." Layer 1 decided a grid runs; this layer decides how the launched work distributes across SMs — and it's the other side of layer 1's kernel-boundary seam: where graphs and PDL soften the boundary from above, persistence, CLC, and megakernels dissolve it from below, turning µs-scale launch costs into ns-scale dispatch inside a resident kernel. The launch geometry frozen by layer 1 is binding here: cluster dims set CLC's steal granularity, and one-wave sizing is what makes persistent designs sound.

Persistent kernels & software tile schedulers

all archsfoundation of stream-K

Launch ~one block per SM and have each pull work items from a global atomic counter until the queue drains. Software dynamic scheduling: blocks keep weights/state resident across items, and slow tiles no longer gate a whole wave. Stream-K GEMM generalizes this by also splitting the K dimension so partial tiles fill the tail wave.

next_tile = device_counter(0)

@kernel
def persistent_kernel(num_tiles):
    while True:
        tile = next_tile.fetch_add(1)     # leader claims, broadcast to block
        if tile >= num_tiles: return
        process(tile)

launch(persistent_kernel, grid=num_sms * blocks_per_sm)  # exactly one wave
__device__ int g_next;

__global__ void persistent_kernel(int num_tiles, ...) {
    __shared__ int tile;
    while (true) {
        if (threadIdx.x == 0) tile = atomicAdd(&g_next, 1);
        __syncthreads();
        if (tile >= num_tiles) return;
        process_tile(tile, ...);
        __syncthreads();
    }
}
// launch exactly one wave:
cudaDeviceGetAttribute(&num_sms, cudaDevAttrMultiProcessorCount, 0);
persistent_kernel<<<num_sms * blocks_per_sm, 256>>>(num_tiles, ...);

Use when

  • Uneven per-tile cost: variable seq lengths, sparsity, stream-K GEMM
  • State (weights in smem/regs) should survive across work items
  • Pre-Blackwell hardware — this is the portable version of CLC

Limits

  • Atomic counter contention at high steal rates (back off spin loops with nanosleep)
  • You size the grid — fights other concurrent kernels for SMs
  • Blocks squat on SMs even when idle; CLC can improve coexistence and remove the global queue, but not create finer-grained work

Threadblock rasterization & tile swizzle

all archsthe zeroth scheduling decisionCUTLASS RasterOrder · Triton GROUP_M

Before any dynamic scheduling, there's a static choice: the order in which tile IDs map to work. Whatever set of tiles is resident at the same moment determines L2 reuse — naive row-major order marches along one row of C, streaming all of B through L2 with little reuse; a grouped/serpentine order keeps concurrent CTAs inside a GROUP×wave window so they share both A rows and B columns. This composes with everything: static grids, persistent loops, stream-K, and CLC all consume a "next tile" that some rasterization function decodes.

def swizzle_tile(tid, grid_m, grid_n):
    width   = GROUP_M * grid_n            # tiles per group
    group   = tid // width
    first_m = group * GROUP_M
    size_m  = min(grid_m - first_m, GROUP_M)
    m = first_m + (tid % size_m)          # snake within the group
    n = (tid % width) // size_m
    return m, n              # concurrent tiles cluster in M => L2 hits
// grouped (Triton-style) rasterization: linear tile id -> (m, n)
__device__ int2 swizzle_tile(int tid, int grid_m, int grid_n) {
    int width   = GROUP_M * grid_n;          // tiles per group
    int group   = tid / width;
    int first_m = group * GROUP_M;
    int size_m  = min(grid_m - first_m, GROUP_M);
    int m = first_m + (tid % size_m);        // snake within the group
    int n = (tid % width) / size_m;
    return {m, n};                            // concurrent tiles cluster in M ⇒ L2 hits
}

Use when

  • Always — it's nearly free and often worth several percent on bandwidth-bound shapes
  • Tune GROUP so a wave's operand footprint fits L2

Limits

  • Static heuristic: the best order depends on shape and L2 size — CUTLASS exposes it as a tunable (RasterOrder / swizzle) for a reason

Cluster launch control (CLC)

Blackwell target-specificPTX clusterlaunchcontrol.*

Hardware-assisted work stealing. Launch a natural grid; a running cluster can request cancellation of a not-yet-launched cluster and, after a successful response, process the canceled cluster's ID. This dynamically balances unequal whole-tile runtimes and avoids a global atomic queue. It does not subdivide an indivisible tile and therefore does not, by itself, eliminate the final underfilled wave of a uniform GEMM.

The op behaves like TMA: one thread issues it, the response completes via mbarrier, and it can multicast to all CTAs of a cluster. Production kernels pipeline it — CUTLASS's PipelineCLCFetchAsync runs a dedicated scheduler warp producing CLC results into a depth-3 pipeline consumed by the MMA, mainloop-load, epilogue-load, and epilogue warps (the scheduler is also its own consumer: it needs the success bit to know when to exit the persistent loop), so steal latency hides under the mainloop. Unlike a fixed persistent grid, clusters can also exit early and let fresh clusters launch later, so CLC kernels coexist gracefully with concurrent kernels and preemption.

Use when

  • Persistent-style kernels on Blackwell: GEMM, attention, uneven tiles
  • Your kernel shares the GPU with other work
  • Via CUTLASS / CuTe DSL tile schedulers or Triton TLX in practice

Limits

  • Blackwell-only; raw intrinsics + mbarrier + proxy fences are fiddly
  • One try_cancel per cluster — extra issuing threads cancel extra clusters

Megakernels

design patternThunderKittens (Hazy) · Mirage MPK · FlashFormer · Ada-MK

Persistence taken to the limit: fuse the entire model — sometimes across multiple GPUs — into one launch, so operator boundaries stop being kernel boundaries. The motivation is measured, not aesthetic: kernel launches cost microseconds each even under graphs (Hazy measured a no-op kernel at ~2.1 µs standalone and still ~1.3 µs inside a CUDA graph), and at decode batch 1 the setup/teardown bubbles between hundreds of small kernels dominate. Two design schools exist, distinguished by who schedules the tasks:

School 1 — statically scheduled interpreter (Hazy Research / ThunderKittens). A compiler/planner assigns each SM its own instruction queue ahead of time. Each instruction is a CTA-sized unit of work ("compute this matmul output tile") structured into explicit load / compute / store sections, and the on-GPU interpreter aggressively pipelines across instruction boundaries — starting the next instruction's weight loads (into paged shared memory) while the current one finishes, which is what eliminates the inter-op memory bubbles. Cross-SM dependencies are global-memory counters; the lineage runs ThunderMLA (fused attention with meta-instructions) → the Llama-1B low-latency megakernel (~78% of H100 memory bandwidth at batch 1) → the 8-GPU Llama-70B kernels, where NVLink communication (via multicast "parallel global layouts") is itself pipelined: the multi-GPU residual add for tile N−1 overlaps compute of tile N, keeping tensor cores, HBM, and NVLink busy simultaneously.

School 2 — dynamic event-driven runtime (Mirage MPK). A compiler lowers the tensor program into an SM-level task graph — dependencies tracked per-tile, not per-operator, with the Mirage superoptimizer generating each task's CUDA — and an in-kernel runtime executes it: SMs are statically partitioned into workers (one per SM, each with its own task queue) and scheduler warps (four per scheduler SM) that poll event queues and dispatch newly-enabled tasks. A task's completion triggers events; events enqueue dependent tasks — including communication tasks, so compute/comm overlap falls out of the graph. Reported gains: 1.2–6.7× latency reduction vs kernel-per-operator baselines, 1.0–1.7× vs SGLang/vLLM. The trade: dynamic dispatch and managed smem paging add branching overhead that hand-scheduled static queues avoid (the critique that motivates Ada-MK's search-based static planner), but the runtime adapts to variable work where a static plan can't.

            case MLP:    run_mlp(instr)
            case WAIT:   spin_until(g.counter[instr.a] >= instr.b)
            case SIGNAL: fence(); g.counter[instr.a] += 1

# School 2: event-driven (MPK-style)
# worker SM:      while True: t = my_queue.pop(); run(t); trigger(t.event)
# scheduler warp: while True: e = poll(); for t in e.deps: workers[rr].push(t)
// School 1: static per-SM instruction stream (Hazy-style, simplified)
struct Instr { int op, arg0, arg1; };   // "attn layer 3, tile 4", "wait counter 7"…
__global__ __launch_bounds__(NUM_THREADS, 1)
void megakernel(const Instr* prog, int n, Globals g) {
    for (int pc = 0; pc < n; ++pc) {     // interpreter; real ones pipeline
        Instr in = prog[blockIdx.x * n + pc];   //   load(pc+1) under compute(pc)
        switch (in.op) {
            case OP_QKV:    run_qkv(in, g);    break;
            case OP_ATTN:   run_attn(in, g);   break;
            case OP_MLP:    run_mlp(in, g);    break;
            case OP_WAIT:   while (atomicAdd(&g.cnt[in.arg0], 0) < in.arg1); break;
            case OP_SIGNAL: __threadfence(); atomicAdd(&g.cnt[in.arg0], 1); break;
        }
    }
}

// School 2: event-driven worker loop (MPK-style, simplified)
// worker SM:    for(;;){ t = my_queue.pop(); run(t); trigger(t.event); }
// scheduler warp: for(;;){ e = poll_events(); for (t : e.dependents) workers[rr++].push(t); }

Inside the SM

Warp specialization

practical on sm_90+setmaxnreg

Split the block's warps into roles — producer warps issuing TMA loads, consumer warps running tensor-core MMAs, plus scheduler/epilogue warps — synchronized by mbarriers. This is software pipelining as warp-level scheduling, and it is how every fast Hopper/Blackwell GEMM, FlashAttention-3, CLC kernels, and megakernels are built. On Blackwell, tcgen05 MMA is itself asynchronous (as Hopper's wgmma.mma_async was, with its fence/commit/wait protocol), so even the MMA is "issued by one warp, awaited by others." The frontier version is heterogeneous-unit pipelining: FlashAttention-4 overlaps the tensor cores against the SFUs (exp) and CUDA cores (rescaling) as additional pipeline agents — necessary because Blackwell's tensor throughput grew far faster than its SFU and ALU throughput.

@kernel
def ws_kernel(...):
    if my_warp in producers:
        registers.shrink_to(40)          # hand regs to the consumers
        while work: tma_load_next(); full[i].arrive()
    else:
        registers.grow_to(232)
        while work: full[i].wait(); mma_tile(); empty[i].arrive()
__global__ void ws_kernel(...) {
    int wid = threadIdx.x / 32;
    if (wid < NUM_PRODUCERS) {
        asm volatile("setmaxnreg.dec.sync.aligned.u32 40;");  // give up regs
        while (work) { tma_load_next_tile(); mbar_arrive(&full[i]); }
    } else {
        asm volatile("setmaxnreg.inc.sync.aligned.u32 232;"); // take them
        while (work) { mbar_wait(&full[i]); mma_tile(); mbar_arrive(&empty[i]); }
    }
}

Warpgroup schedules: cooperative vs ping-pong

sm_90sm_120 familysubsumed by TMEM on sm_100

Given warp specialization, the next question is how the consumer warpgroups divide work. Two canonical answers, named after the CUTLASS kernel schedules:

Cooperative — two consumer warpgroups split one large output tile (each takes half of a 256×128 tile), mainloop together, epilogue together. Simple, big tiles, but the epilogue's latency sits exposed at the end of every tile: while results convert and store, the tensor cores idle.

Ping-pong — the two consumer warpgroups own different output tiles, phase-shifted: while warpgroup A runs its mainloop, warpgroup B runs its epilogue, then they swap, coordinated by named barriers (with the shared TMA producer feeding both). The epilogue is completely hidden behind the other warpgroup's MMAs — at the cost of two accumulators' worth of register pressure and trickier barrier choreography.

Layer 4

Data movement & where to put things

Scheduling is also deciding where bytes should wait and which engine moves them. Blackwell adds specialized tensor memory, while each mover—ordinary loads/stores, copy engines, cp.async, bulk/TMA, DSMEM operations, and tcgen05—has a different issuer and completion contract.

all regimesNot a fourth rung — the object the other rungs schedule. Layers 1–3 decide when and where compute runs; this layer catalogs the transfers that all of that overlapping exists to hide, spanning every regime of the ladder (ns smem hops to µs host copies). It sits fourth for a reading-order reason, not an architectural one: its completion contracts (mbarriers, bulk groups, tcgen05.wait) only make sense after layer 3 introduced the machinery. In tuple terms, layers 1–3 answer when is work ready / who runs it; this layer answers where state lives, how it moves, how completion is observed.

Completeness checklist: orchestration techniques

These mechanisms are less Blackwell-specific but often win before low-level PTX:

  • Graph composition/update: child graphs, empty fan-in/fan-out nodes, event nodes, external-semaphore nodes, allocation/free nodes, edge data/ports, cudaGraphExecUpdate, per-node update, upload, and first-launch warm-up.
  • Graph capture: global/thread-local/relaxed modes, multi-stream fork/join through events, dependency-update APIs, capture invalidation, and capture into an existing graph.
  • Batch work before scheduling it: cuBLAS grouped/batched GEMM, cuBLASLt, CUTLASS grouped schedulers, and NCCL group calls often beat many tiny independent launches.
  • Host continuations: cudaLaunchHostFunc queues CPU work after preceding stream commands without blocking the submitting thread; the callback must obey CUDA API restrictions.
  • Avoid hidden serialization: understand legacy NULL-stream semantics, per-thread default streams, synchronous allocation/page-locking/configuration calls, and prefer stream queries/events over broad cudaDeviceSynchronize().
  • Resource sharing ladder: launch priority (hint) → execution-affinity SM-count limit → MPS resource limiting / static SM partitioning → MLOPart locality devices (B200/B300) → green-context SM resource partition → MIG hardware instance.   • Device work discovery: persistent atomic queues, hierarchical queues, work donation/stealing, Stream-K/split-K, CLC, CDP2, device graphs, and megakernels solve different kinds of dynamism.
  • Multi-device: ordinary graphs do not automatically schedule a distributed DAG; encode peer copies/events or use NCCL/NVSHMEM. Multi-device cooperative launch has stringent support constraints.
Worked example

One algorithm, every technique: matmul

C = A·B, taken from naive to state of the art. Each stage names the profiler symptom that motivates it, the technique that fixes it, and what it buys. Read top to bottom: this is roughly the actual optimization order.

0

Baseline: one CTA per output tile

Launch a (M/128, N/256) grid, each block computes one tile: load A and B fragments to smem with plain ld, __syncthreads(), MMA, store. The hardware scheduler assigns blocks to SMs. This already gets decent occupancy — everything below fixes a specific way this leaves performance on the table.

1

Tensor cores idle between loads → TMA + warp specialization + mbarriers

Symptom: the MMA pipe sits idle while every warp does address math and waits on gmem. Fix: split roles — one elected thread issues TMA tile loads into a 3–5 stage circular smem buffer; producer warps drop to 40 registers via setmaxnreg, consumer warps take 232 and run MMAs; full/empty mbarriers coordinate. Buys: gmem latency fully hidden behind compute; this is the single largest jump, from ~30–40% to >80% of peak on a big square GEMM. (On sm_80 hardware, cuda::pipeline + cp.async is the same idea in portable form.)

2

MMA stalls while results drain → TMEM double buffering Blackwell

Symptom: on Hopper, the accumulator lives in the consumer warpgroup's registers, so the mainloop can't start tile N+1 until the epilogue finishes post-processing tile N — the classic fix being the ping-pong schedule, which buys the overlap with a second warpgroup's registers. Fix: on sm_100, tcgen05.mma accumulates into TMEM. A 128×256 f32 tile needs 256 of the 512 columns — so allocate both halves and ping-pong: MMA writes buffer A while the epilogue warpgroup drains buffer B via tcgen05.ld, converts, and TMA-stores. Buys: mainloop and epilogue fully overlap, and the register file is freed for epilogue fusion (bias, activation, quantization) instead of accumulator storage.

3

Bandwidth-bound on operand loads → clusters + TMA multicast

Symptom: neighboring tiles in a column all read the same B tile; each CTA fetching its own copy doubles gmem traffic. Fix: launch 2×1 clusters — the two CTAs sit on paired SMs, one TMA multicast fills both CTAs' smem from a single gmem read, and 2-SM tcgen05.mma (cta_group::2) lets the pair share operands outright. Request 4×1 as a preferred dim with 2×1 fallback so fragmented SMs don't stall launches. Buys: up to half the operand traffic; on bandwidth-bound shapes this is the difference between compute-bound and not.

4

The tail wave → stream-K, then CLC Blackwell

(Order matters before balance: pick the tile rasterization first — grouped ordering so each wave's operands fit in L2 — then fix the tail.) Symptom: wave quantization. Concretely: M=N=4096 with 128×256 tiles gives 32×16 = 512 tiles. A B200 has 148 SMs, so 512/148 = 3.46 waves — three full waves, then a tail wave with 68 of 148 SMs busy. That last wave runs at 46% utilization, wasting ~13% of the whole kernel. Gets worse for skinny shapes.

Fix: split the K dimension of leftover tiles with Stream-K/split-K (or choose a smaller output tile) so idle SMs receive real parallel work; reduce partials through a workspace, which can be allocated with cudaMallocAsync. CLC is complementary: it can distribute those decomposed or unequal-cost work units without a hot global software queue, but stealing the original 68 whole tiles cannot manufacture another 80 tile computations. For uniform indivisible tiles, CLC alone does not remove wave quantization.

5

The GEMM has neighbors → streams, graphs, PDL

Zoom out: your matmul lives in a network. Three distinct situations, three tools:

Independent GEMMs (MoE experts, batched heads, different requests): concurrent streams — or better, one grouped/batched GEMM kernel, since on-GPU scheduling beats stream-level scheduling when shapes are known. A chain of dependent GEMMs (transformer MLP: up-proj → activation → down-proj): PDL, so down-proj's TMA descriptor setup and weight prefetch overlap up-proj's tail — worth a few µs per pair, which at decode batch 1 is a real fraction of each layer. Hundreds of small GEMMs per step (a full decode pass): capture the step into a graph with PDL edges baked in; replay for one launch per token instead of hundreds.

6

GEMM vs the all-reduce → priorities, sync domains, green contexts

Symptom: tensor-parallel training/inference overlaps GEMM with NCCL, but the comm kernel's blocks queue behind three waves of GEMM blocks, and its heavy membar fences stall GEMM warps. Fix, in escalating order: high-priority stream for NCCL (dispatch-order hint) → cudaLaunchMemSyncDomainRemote on the comm kernels so their fences stop interfering → a green context reserving ~16 SMs so comm always has hardware. Note the interplay with stage 4: a CLC/persistent GEMM sized to "all SMs" would starve the comm slice — CLC's cancel-based model handles this gracefully, a fixed persistent grid does not.

7

Dissolve the kernel boundary → megakernel

End state for batch-1 decode: the GEMMs stop being kernels at all. Each becomes an instruction ("MLP layer 12, tiles 0–47") in a per-SM program; dependencies become per-tile counters, so down-proj tiles start as soon as their up-proj inputs exist rather than waiting for the whole layer; weights for layer N+1 stream via TMA into paged smem while layer N computes. Stages 1–4 all survive inside — the megakernel is those same warps and pipelines, minus the launch boundaries.

What honestly doesn't apply — GEMM is regular, so the irregular-work tools stay in the drawer: dynamic parallelism (no data-dependent work discovery), conditional nodes (no on-device control flow — unless the GEMM sits in an iterate-to-convergence solver), device graph launch (no on-GPU dispatch decision). Knowing a technique is irrelevant is as useful as knowing it exists — the BFS walkthrough below is where each of those tools becomes load-bearing. Two adjacent knobs that do matter: an L2 persisting window on weights for GEMV-shaped decode, and MPS/MIG only once this GEMM serves multiple tenants.

Worked example II

The irregular half: frontier BFS

Breadth-first search over a graph is the canonical irregular workload: the amount of work per step is discovered at runtime, per-vertex cost varies by orders of magnitude (degree 2 vs degree 2M), and nothing tiles. It stands in here for adaptive mesh refinement, tree/BVH traversal, and sparse factorization — every tool the matmul walkthrough rejected is load-bearing below.

0

Baseline: one kernel per frontier level, host in the loop

Each level: launch an expand kernel over the current frontier, copy the new frontier's size back to the CPU, decide whether to loop. Symptom: a device→host round trip plus a launch per level — for a high-diameter graph (road networks: thousands of levels of tiny frontiers), the CPU round trips cost more than the traversal.

while True:
    launch(expand, grid=blocks(front_n), stream=s)
    copy_async(h_n, d_next_n, stream=s)
    s.synchronize()                 # <- the bottleneck: host round trip / level
    if h_n == 0: break
    front, next = next, front;  front_n = h_n
while (true) {
    expand<<<blocks(front_n), 256, 0, s>>>(front, front_n, next, d_next_n);
    cudaMemcpyAsync(&h_n, d_next_n, 4, cudaMemcpyDeviceToHost, s);
    cudaStreamSynchronize(s);              // ← the bottleneck
    if (h_n == 0) break;
    std::swap(front, next); front_n = h_n;
}
1

Kill the host round trip → conditional WHILE node or device graph launch

The loop condition lives in GPU data, so let the GPU evaluate it. Wrap {expand, compact, check} as the body of a WHILE conditional node: the check kernel calls cudaGraphSetConditional(h, next_n > 0) and the graph re-runs its body with zero CPU involvement. The device-graph alternative: the check kernel tail-launches the level graph again (cudaStreamGraphTailLaunch), a self-scheduling pipeline. Buys: the per-level cost drops from a sync + launch round trip to on-device dispatch; for the road-network case this is the single biggest win, exactly as graphs were for decode. This is the "iterate-until-converged" pattern the matmul note said would justify these tools.

2

Degree skew → binning + CDP2 fire-and-forget

Symptom: one thread per frontier vertex means the thread holding the 2M-degree hub runs 10⁶× longer than its warp-mates; the whole grid waits on one lane. Fix: classify by degree during expansion — small vertices handled per-thread, medium per-warp (ballot + prefix sum to divide edges), large per-CTA. For the rare monster vertex, the canonical dynamic-parallelism use finally appears: launch a child grid sized to its edge list, discovered at runtime, impossible to size from the host.

@kernel
def expand(front, q):
    v = front[global_thread_idx()]
    deg = row[v + 1] - row[v]
    if   deg <= 32:   expand_per_thread(v)
    elif deg <= 4096: q.warp_bin.push(v)         # re-binned, warp-cooperative
    else: launch(expand_hub, grid=blocks(deg),   # canonical CDP2: child
                 stream=FIRE_AND_FORGET)         # sized by runtime data
__global__ void expand(const int* front, int n, WorkQueues q) {
    int v = front[blockIdx.x * blockDim.x + threadIdx.x];
    int deg = row[v + 1] - row[v];
    if      (deg <= 32)   expand_per_thread(v);
    else if (deg <= 4096) push(q.warp_bin, v);      // re-binned, warp-cooperative
    else expand_hub<<<blocks(deg), 256, 0,          // canonical CDP2:
                       cudaStreamFireAndForget>>>(v); // child sized by data
}

Note the priority order: binning (cheap, no launch) handles 99.9% of skew; CDP handles the tail where a child launch's ~µs overhead is amortized over millions of edges. Using CDP for every vertex is the classic anti-pattern — per-launch overhead swamps small children.

3

Fuse the whole traversal → persistent kernel + global work queue

The irregular analog of the megakernel: launch one wave of blocks that run for the whole search, pulling vertices from a global queue (atomic head/tail) and pushing discovered neighbors back. Level boundaries become counters or vanish entirely (for algorithms tolerant of async traversal); idle blocks spin with nanosleep backoff on an empty-but-not-done queue. This is where the sync-model table earns its place: the queue needs acquire/release atomics at device scope, and forward progress needs care — a block waiting on work that only a not-yet-scheduled block would produce is a livelock, which is why the grid must fit in one wave (cooperative launch guarantees it).

@kernel
def bfs_persistent(q):
    while True:
        v = q.try_pop()                # acquire semantics
        if v is None:
            if q.done(): return        # drained AND no producers
            nanosleep(200); continue   # back off, don't hammer
        for u in neighbors(v):
            if claim(u): q.push(u)     # release semantics
__global__ void bfs_persistent(Queue q, ...) {
    while (true) {
        int v;
        if (!q.try_pop(&v)) {                     // acquire semantics
            if (q.done()) return;                  // drained AND no producers
            __nanosleep(200); continue;            // back off, don't hammer
        }
        for (int e = row[v]; e < row[v+1]; ++e)
            if (claim(col[e])) q.push(col[e]);     // release semantics
    }
}
4

The Blackwell angle → CLC, with its honest limit

Within one level, frontier work is exactly CLC's shape: launch one block per frontier vertex (or per bin chunk), let the first wave steal pending blocks, and skew balances in hardware with no atomic queue. But note the boundary: CLC redistributes blocks that were in the launched grid — it cannot cover work discovered after launch. So CLC replaces the software queue for the per-level kernels of stage 1, while the fully-fused stage 3 still needs its own queue for dynamically discovered vertices. The two compose: CLC-drained level kernels inside a device-graph WHILE loop is a clean Blackwell BFS.

5

External producers → doorbells and NVSHMEM signals

When frontier work arrives from outside — another GPU's partition of the graph, a NIC, a host thread — the waiting becomes scheduling. Stream-ordered: gate the next level's graph on cuStreamWaitValue32 against a doorbell word. In-kernel (persistent version): the queue's producers are remote — NVSHMEM put + signal into this GPU's queue, with nvshmem_signal_wait_until as the consumer's blocking pop. Multi-GPU BFS is precisely this: partition the graph, push remote-owned discovered vertices to their owner's queue, terminate via a distributed all-drained check.

What honestly doesn't apply here — the mirror image of the matmul list: TMA (irregular gathers have no dense tiles to describe — plain loads and cp.async do the memory work), TMEM/tcgen05 (no MMA), ping-pong and rasterization (no tile structure, no L2 tiling locality — though vertex reordering for locality is the graph-world cousin), and PDL only weakly (each level's size gates the next; there's little independent prologue to overlap). One matmul tool that returns unchanged: priorities / green contexts if the traversal shares the GPU with other work.
Background

Forty years of CPU concurrency, re-derived on a GPU

If the menu above feels like it lacks a "right answer," that's inherited. The CPU world never converged on one concurrency model either — but it converged on an explanation for why it can't, and every school it produced has a direct counterpart in this guide. Reading the toolbox through that lens turns an arbitrary list into a taxonomy.

The schools, mapped

First, why so many models exist at all: "concurrency" conflates at least seven separate questions — what the units of work are, what ordering exists between them, who owns mutable state, how tasks communicate, how ready work maps onto processors, how overload is bounded, and how completion and failure propagate. Different systems answer different subsets, which is also why comparing streams, CLC, TMA, and TMEM head-to-head feels confusing: they live at different layers of that list (made explicit in the decision rule below).

The founding observation (Lee, The Problem with Threads, 2006; Ousterhout, Why Threads Are a Bad Idea, 1995): unrestricted shared-state threading makes programs nondeterministic by default and asks humans to prune an exponential interleaving space by hand. Every durable school of concurrent programming is a different choice of what freedom to take away — and each GPU technique here is one of those restrictions, re-implemented under GPU constants.

Three results that transfer

Structure beats freedom. Every CPU model that won did so by making a class of bug inexpressible — data races unrepresentable in CSP, deadlocked joins unrepresentable in fork-join. The GPU stack has been recapitulating that march for a decade: from "spin on an atomic and hope" toward typed pipelines, explicit completion contracts, and driver-validated graphs. Practical corollary: given two techniques of similar performance, prefer the one whose restrictions make your likely bug impossible, not the one with the most headroom.

The Lauer–Needham duality (1979). Message-passing and shared-memory systems are formal duals — equivalent in expressiveness and performance, differing only in which mistakes they invite. This is the deep reason "no consensus" is the stable end state: the models are interconvertible, so the choice is ergonomic and workload-shaped, not correctness-shaped. The two worked examples are this theorem in practice: matmul wants the dataflow school (static schedules, declared dependencies); BFS wants the stealing and messaging schools. Neither is "right"; each matches its workload's structure.

Two-level (M:N) scheduling. The CPU endgame was user-level tasks multiplexed onto kernel threads (scheduler activations, Go's runtime) sitting on OS-level partitions (cpusets, cgroups). The GPU stack is the same sandwich: work items multiplexed onto persistent blocks or CLC-drained grids (layer 2), which sit on green contexts, MPS/MLOPart, and MIG (layer 5). The lesson that transfers: keep the levels separate. Application-level load balancing and machine-level resource partitioning are different problems; entangling them (a persistent grid hard-sized to "all SMs" doing double duty as a partitioning decision) reproduces the classic pitfalls the CPU world spent the 1990s escaping.

What doesn't transfer — and where to read instead

The mainstream CPU schools all lean on one hidden subsidy: a preemptive OS scheduler with cheap context switches. "Spawn a million goroutines and let the runtime sort it out" works because a blocked task costs almost nothing and can always be descheduled. GPUs revoke the subsidy. Blocks are cooperatively scheduled, occupancy is the hard currency, and forward progress is the programmer's problem — the reason the BFS persistent kernel needed its one-wave guarantee, and the reason a block spinning on work that only an unscheduled block would produce is a livelock, not a slow day.

So the closest CPU literature isn't the mainstream threading canon but its harsher corners: cooperative fibers and run-to-completion event systems (where yielding is manual and starvation is your fault), static real-time scheduling (fixed resources, admission control, worst-case reasoning — the natural frame for megakernel instruction planning), and the lock-free progress taxonomy (Herlihy: wait-free ▸ lock-free ▸ obstruction-free), which maps directly onto auditing spin loops in persistent kernels — a CLC steal loop is lock-free (someone always makes progress), while a naive two-phase handshake between blocks may be neither. When a device-side design feels underspecified, these three bodies of work are where the missing arguments live.

The duality, sharpened: where does waiting work live?

Lauer–Needham compresses to one operational question: when an activity cannot make progress, where is the suspended computation represented? Two answers exist. In a paused execution context — program counter, registers, stack — or in queued data plus explicit state — a descriptor, event, or state-machine record. Threads vs events, monitors vs server loops, futures vs callbacks are all this one choice wearing different clothes, and the durable conclusion is that the representation should follow the machine substrate, not ideology.

The GPU instance is exact. An ordinary oversized grid represents waiting work as data: the hardware holds unstarted block indices — each one literally a queued work descriptor — and materializes execution contexts as resources free. A persistent kernel flips the representation: long-lived resident contexts pull explicit descriptors from a software queue. The same computation, both ways — and each representation's cost is concrete: a waiting resident context holds registers and smem that other work can't use; a waiting descriptor holds queue slots, atomics traffic, and cache. CLC is an unusually literal bridge between the two — unstarted block index → stolen descriptor → processed by a resident context — which is the deep reason it combines persistent workers' locality with an ordinary grid's scheduling freedom. One level down, a warp-specialized pipeline is the same duality inside an SM: full/empty mbarrier phases are the message view; the smem stages they guard are the shared-state view.

Lee's paper then adds the discipline the duality doesn't: his argument is not "messages good, shared memory bad" (a mailbox with racing senders is just as nondeterministic) — it's determinism first, nondeterminism confined and explicit. The GPU translation is a rule this guide should state outright: scheduling may be nondeterministic; correctness must not depend on the schedule. CLC is the perfect test case — if every block index names an independent tile, stealing changes performance and not the answer; if blocks race through order-sensitive global state, the steal schedule leaks into program semantics. One subtlety worth its own sentence: distinguish mathematical from bitwise determinism — floating-point atomic reductions can be order-independent in exact arithmetic yet bitwise order-dependent, because fp addition isn't associative. Decide which one you're promising before you let the scheduler choose.

Design rules this yields — define tile ownership and producer/consumer edges before assigning warps or CTAs; use the narrowest communication scope that works (warp → block → cluster → device); default to ordinary grids for regular independent work (the hardware block queue is already an efficient work queue) and pay for persistence/specialization only when it buys overlap, state reuse, or load balancing; represent buffer ownership with explicit barrier phases, never inferred warp timing; and treat the context-vs-descriptor choice as a resource decision about which memory holds your waiting work.

What actually reached consensus

Beneath the school wars, five points did converge — and each lands directly on GPU practice:

1. Data races are not a programming model. Modern memory models settled on happens-before + data-race freedom: racy programs are undefined; race-free programs get simple semantics. The GPU translation: relaxed atomics are primitives for building models (queues, counters, doorbells), not a pleasant application-level model — use them only where you can state the invariant and prove the ordering, which is what the sync-model table exists for.

2. Logical concurrency ≠ physical parallelism. Expose a million tasks; map them onto a bounded set of workers (the Cilk T₁/P + O(T∞) result). GPU translation: the number of tiles is not the number of resident CTAs or streams — that gap is precisely what persistent queues, CLC, and rasterization functions manage. Confusing the two levels is how you get a grid hard-sized to the machine doing double duty as a partitioning decision.

3. Concurrency needs lifetime structure. Structured concurrency (child work completes, fails, or is cancelled before its scope exits) eliminated orphan tasks on CPUs. Honest assessment: CUDA has little native structure here — graphs come closest (a launch is a scoped unit with known contents); ad-hoc streams, fire-and-forget CDP children, and device queues make it easy to create work whose lifetime nobody can state. Treat that as a cost when choosing.

4. Prefer ownership and partitioning over synchronization. The most robust synchronization is eliminated sharing: partition, own exclusively, accumulate locally then reduce, transfer ownership rather than share writable aliases. This is the right frame for GPU memory placement — which CTA owns this smem tile; which warp owns this pipeline stage; is this TMEM buffer producer-owned or consumer-owned right now; when exactly does ownership transfer after a TMA completes? Every mbarrier phase flip in a warp-specialized pipeline is an ownership transfer; naming it that way makes the barrier protocol legible.

5. Bound in-flight work; provide backpressure. An async API that lets producers create unlimited work is incomplete — CPU reactive systems added explicit demand signaling for this reason. The GPU analogues: fixed pipeline stage counts, bounded persistent queues, capped in-flight TMA transactions, and producers forbidden from overwriting buffers consumers still own. Double and triple buffering are not just performance techniques — they are backpressure protocols, with the empty/full mbarrier pair as the demand channel.

A working decision rule

The reason comparing streams, CLC, TMA, and TMEM head-to-head feels confusing is that "concurrency" conflates separate questions — what the units of work are, what ordering exists, who owns mutable state, how tasks communicate, how ready work maps to hardware, how overload is bounded, how completion propagates. Each mechanism in this guide answers a subset. Laid out by question:

If a slot is blank, the design is incomplete; if two mechanisms fill the same slot, one is redundant. The mechanisms compose along the tuple — they are almost never mutually exclusive alternatives.

And the literature's closest thing to a verdict, translated: describe dependencies and ownership first — scheduling is an implementation decision. Use structured task DAGs for control, ownership for state, bounded queues for capacity, and let a runtime (driver, CLC, scheduler warps) place the ready work. Drop to raw atomics, fences, and hand-rolled schedulers only where measurement justifies it.

What traces cannot tell you

The ncu replay trap — ncu replays kernels serially and in isolation, flushing caches between passes by default. This destroys exactly the effects several techniques create: PDL overlap, graph packing, cross-kernel L2 reuse, and concurrent-stream interaction are invisible or actively distorted under ncu. Measuring a PDL or graph win in ncu is a category error — those live in nsys timelines or raw CUDA-event timing under production concurrency.

Two further limits. Traces show the design you have, not the counterfactual: a kernel-per-op profile never displays "a megakernel would buy X" — you do the gap accounting yourself (sum the inter-kernel bubbles plus the intra-kernel memory stalls that cross-op pipelining would hide; that arithmetic is how the megakernel papers motivate themselves). The profiler ranks symptoms; it does not price cures. And the tuple layer is invisible: no counter measures ownership structure, backpressure bounds, forward-progress soundness, or whether the dependency graph is at the right granularity — a profile can show the atomic queue is contended, not that the queue shouldn't exist. Profiles select within a design; the tuple designs.

Blackwell-specific caveat: counter coverage for the newest machinery (tcgen05 pipes, TMEM traffic, CLC behavior) has arrived incrementally across Nsight releases — for CLC you mostly observe effects (balanced per-SM cycles, no tail wave) rather than steals themselves. Keep Nsight current, and don't read a missing counter as missing activity.
